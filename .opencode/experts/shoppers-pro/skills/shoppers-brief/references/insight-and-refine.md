# 需求洞察与卡片成文方法（insight & refine）

> **何时加载**：Phase 2（写 `10-insight.json`）与 Phase 5（写 `50-final.json`）前必读。两个环节都是纯推理，不调检索工具。
> **契约关系**：洞察定下全流程的「当前用户」口径（Phase 3 选品、Phase 4 排序、Phase 5 成文都按它对齐）；Phase 5 把 `40-ranked.json` + `30-reputation.json` 按 id 合流成 `50-final.json`。

## 一、需求洞察（Phase 2 → 10-insight.json）

读 `<run>/00-input.json`，提取 `messages`（完整对话，含历轮追问与回答，最后一条是最新补充、权重最高）、`brief`、`current_date`，生成需求洞察写入 `<run>/10-insight.json`。

这是系统的信任入口——用户的信任来自「它把我要害说准了」，**不是**来自情感上的拔高或煽情。购物就是购物，不要替用户把它升华成情感叙事或人生意义。

### 洞察生成规则

1. **headline**：一句洞察标题，说清用户具体要解决什么问题；不复述原话，不罗列参数，不用"这不是X而是Y""比参数更重要"这类拔高句式。
2. **empathySummary**：2~4 句**务实需求分析**，只写三件事——
   - ① 用户具体要解决什么问题（基于对话和简报，不脑补）
   - ② 选择时绕不开的**技术性/实用性**顾虑（存储/续航/散热/重量/便携/易用性/售后等，来自 brief 的 implicitConcerns 和品类常识）
   - ③ 最关键的一道取舍（通常对应预算卡位，或核心维度之间的冲突）
3. **decisionPriorities**：3~5 个决策重点，按"当前用户"的重要性排序（例如给父母用时，易用性/续航/售后要排到性能前面）。
4. **禁止情感拔高**：不要把购物升华成情感、关系或人生叙事。禁用"这不是X而是Y""陪伴机""心意""投资""长期陪伴""得体""体面""一份XX"等把商品与情感/身份绑定的词。用户花多少钱买什么，就是买什么。
5. **禁止揣测用户潜台词**：不要脑补用户没说出口的内心戏（如"长辈的心意""孩子会不会嫌弃""同学圈认同感"）。规则 2 里"绕不开的顾虑"特指**技术性/实用性**的（如玩原神要考虑散热、用四年要考虑存储），**不是情感性的**。只有当用户在对话里明确表达过某种情感诉求时，才可以写入。
6. **语气克制务实**：像懂行的朋友帮你列购买重点，而不是写情感软文或营销文案。直接、具体、不煽情。绝不写套在任何人身上的通用文案（如"性价比高""做工精良"）。
7. 如果用户在对话里做了修改/补充，洞察要反映最新需求，而不是最初的版本。

### 写法对照（务必遵守）

场景：给上大学的女生挑 iPhone，预算 7500~8500，玩游戏+拍照+剪辑+追番，最看重性能。

❌ 过度共情（禁止这样写）：
> 您这不是单纯买台手机，是想给外甥女的大学四年配一台「样样能打」的陪伴机——一份得体的升学心意。她没说但您该替她想到的，是同学圈的认同感……

✅ 务实洞察（正确写法）：
> 她要一台能扛四年、玩游戏不掉帧、拍照剪辑都跟手的 iPhone。7500~8500 正好卡在 iPhone 17 顶配和 17 Pro 入门之间，关键取舍是要不要为 Pro 的更强芯片和长焦多掏一千多。存储别抠门、续航撑全天、重量手感顺眼，是这几个预算下没说但绕不开的点。

差别：前者升华情感、揣测潜台词；后者只陈述事实性的问题、技术顾虑和取舍。

### 输出契约

`<run>/10-insight.json`（UTF-8，只写这一个 JSON 对象）：

```json
{
  "needInsight": {
    "headline": "一句洞察标题",
    "empathySummary": "2~4 句务实需求分析",
    "decisionPriorities": ["决策重点1", "决策重点2", "决策重点3"]
  }
}
```

## 二、卡片润色与决策报告（Phase 5 → 50-final.json）

读 `<run>/00-input.json` + `<run>/40-ranked.json` + `<run>/30-reputation.json`，把口碑按 `id` 挂回商品（`30-reputation.items[].id` ↔ `40-ranked.products[].id`），对每款写针对当前用户的卡片文案，并写约 500 字决策报告，写入 `<run>/50-final.json`。

与口碑采集的分工：采集负责**事实**（共性槽点是什么、评分多少）；这里负责**把事实翻译成对当前用户有用的建议**——同样一条「主板虚焊」共性槽点，给极客写「追求极限性能可忽略」、给父母写「直接劝退，售后风险高」。

### 降级规则（失败不阻塞）

- `40-ranked.json` 不存在或读失败（比价线失败）：不报错，改读 `20-candidates.json` 以未排序候选降级——按列表顺序出卡、不写推荐指数与分组，报告里注明「未完成比价排序」。
- `30-reputation.json` 不存在或读失败：按"无口碑"降级——每款的 tradeoff 基于该款 summary 与价格信息自行起草，aiSummary 不引用口碑，reputation 字段输出 `{"dataSource": "model_memory", "confidence": 0.2}`（标识未联网核实），继续往下写报告。
- 某款口碑 id 匹配不上：该款 reputation 留空（同上降级）。

### 卡片润色规则

- 同一商品在不同用户场景下，文案必须不同。
- `aiSummary`：1~3 句，必须同时回答"它最适合当前用户的地方"与"需要接受的取舍"。**取舍要优先采用口碑采集提供的共性槽点**（如果有），比纯模型记忆更可信。
- `fitReasons`：2~3 条，针对当前用户（使用对象/场景/预算）的具体理由；可参考口碑的 `commonPraises`，但要用针对当前用户的口吻改写，不要照搬原文。
- `tradeoff`：1 条，用户需要接受的主要取舍；**优先来自 `commonComplaints` 里与当前用户场景最相关的那条**（如给父母推荐手机时，「主板虚焊」比「拍照夜景一般」更重要）。
- `reputation`：**直接透传**采集给出的 reputation 对象（含 rating / commonPraises / commonComplaints / longTermNotes / categoryIssues / dataSource / confidence / sources），不改字段名、不改 dataSource 值——Phase 6 呈现据此显示「未联网核实」标识。
- aiSummary 不复述参数，不写套在任何人身上的通用文案（如"性价比高""做工精良"）。
- 保留 `40-ranked.json` 里原有其它字段（id/title/brand/model/recommendationIndex/recommendationLabel/offers 等），只覆盖或补充 `aiSummary` / `fitReasons` / `tradeoff` / `reputation`。
- **口碑融入的写法对照**：
  - ❌ 差（堆砌）：「该机型评分 4.7、共性槽点是发热、长期反馈续航衰减」——这是数据堆砌，没翻译成对用户的建议。
  - ✅ 好（翻译）：「性能同档领先，但你常玩原神要接受长时间游戏降频这条共性槽点；散热短板对日常使用影响不大」——把口碑和当前用户场景绑定。
- **诚实降级**：若该款 reputation.dataSource 为 `model_memory`，aiSummary 里不要写得像"经实测"——用「公开渠道口碑样本少，以下基于品类常识」「据公开反馈」等克制措辞。

### 决策报告规则（约 500 字）

1. 第一段直接给最终结论：最推荐哪款（或主推 + 备选），一句话说清为什么是它。
2. 再用 3~4 个短段落，每段以【小标题】开头：
   - 【为什么是它】：结合用户场景说首选款核心理由（不堆参数）。
   - 【要接受的取舍】：首选款或该价位的主要妥协，**优先引用抓到的共性槽点**，比泛泛而谈更可信。
   - 【性价比与备选】：预算内更划算的选择；什么时候值得加预算上更高档。
   - 【怎么买】：推荐平台与下单时机（大促/日常），**收货要重点检查什么**（来自口碑里的常见问题，如「这款有阴阳屏概率，收货先全屏看一遍」「美妆注意辨别真伪」）。
3. 全程针对当前用户的使用对象 / 预算 / 隐含顾虑，禁止通用套话。
4. 总字数约 500 字（中文）。纯文本，段落之间用空行分隔，除第一段结论外每段以【】小标题开头。
5. 不要罗列参数表，不要重复商品卡片里已有的句子。
6. **若所有款 reputation 都为 model_memory**：报告里加一句「公开渠道口碑样本有限，建议下单前自己看一眼京东/天猫的差评区，重点看近 3 个月反馈」。

### 输出契约

`<run>/50-final.json`（UTF-8）：

```json
{
  "products": [
    {
      "...原 40-ranked 字段...": "...",
      "aiSummary": "针对当前用户、融入口碑的总结",
      "fitReasons": ["..."],
      "tradeoff": "优先来自 commonComplaints 的取舍",
      "reputation": { "...采集给出的原对象..." }
    }
  ],
  "report": "约500字决策报告正文"
}
```

### 纪律

- reputation 字段必须**原样透传**，不要改写 dataSource / confidence / sources——这些是数据可信度的标识，Phase 6 呈现依赖它。
- 不调任何检索工具，纯推理。
- 不要修改 `00-input.json` / `40-ranked.json` / `30-reputation.json`。
