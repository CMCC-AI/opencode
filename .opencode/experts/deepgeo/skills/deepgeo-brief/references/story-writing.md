# 故事大纲、成文与图表

报告读者是经营者和管理者，不是工程师。先定故事线，再成文；图表为故事服务。

## 1. 故事大纲（写 40-report.md 前先落 30-outline.md）

一条连续的故事线，每章回答一个普通读者会追问的问题：

```
我们到底在找什么样的点位（决策问题与约束）
→ 人流能不能留下（客流与有效停留）
→ 留下的人是不是目标顾客（客群匹配）
→ 周边商业是在带客还是分流（业态协同与竞争）
→ 好位置能不能成为好生意（成本、财务与风险）
→ 几个候选之间为什么这样取舍（评分、稳定性与否决）
→ 接下来应该做什么（推荐分级、进入条件、签约前验证）
```

运营型场景把"客流/客群/商业"三问换成"分区供需错配在哪、游客结构说明什么、四类动作怎么配"。用户指定章节时服从用户。

## 2. 成文纪律

- 开头 2—3 个自然段把**结论、理由、行动边界**说清楚，随后按大纲展开；
- 每段：先读者能理解的现实现象 → 数据说明了什么 → 为什么影响本次决策；
- 不连续罗列数字；不让段落变成指标播报；段落之间有承接；
- **技术翻译成人话**（正文禁出现 recipe 名、运行编号、字段名、文件路径、"data_mode=xx"）：
  - 不写"min-max 标准化与权重扰动"；写"把不同量纲的指标放到同一把尺子上，再反复调整各因素的重要程度，观察排序会不会改变"；
  - 不写"蒙特卡洛亏损概率"；写"把票价、上座率、成本在合理范围内随机组合一万次，看这个点位有多少次会亏损"；
  - 不写"Cramér's V 为 0.55"；写"目标客群占比高的日子通常有效停留也多，但只能说明两者经常一起变化，不能证明因果"；
  - 不写"z-score 供需缺口"；写"把需求热度和周边供给放在同一尺度比较，找人多而同类供给不足的位置"。
- 每章核心发现标注证据等级对应的措辞档位（是/可能是/建议验证）；
- 表格总量 ≤4 张且只用于横向比较；列表只用于行动步骤/检查项，全文列表行 ≤12 行；
- 末章固定为**"这份结论该怎样使用"**：数据模式边界（模拟/真实）、最重要的不确定性、签约或调整前需现场验证的事项。不附全量指标表与问题台账。
- 默认篇幅 4000—8000 字；用户指定时服从用户。

## 3. 图表纪律（正式图 4—8 张）

- 每张图只回答一个读者能**复述**的问题，紧跟在解释它的段落之后；
- 标题用业务语言："云澜广场留下来的潜在观众最多"，不是"有效停留 metric 排名（run AN-001）"；
- 复杂口径放简短图注；图面不出现运行编号、字段名、路径；
- **最高级断言**（最高/最低/最短/第一/垫底等）必须与配方输出核对；展示精度下并列时标题列出全部并列对象；
- 模拟数据图表：标题或图注含"模拟数据，仅用于演示"；
- 红色只用于风险与异常；普通序列用商务蓝体系（#173f5f/#2d6da3/#6b9bd1/#c9a227 点缀）；
- 坐标轴不截断夸大差异。

## 4. 61-quick-charts.json 写法

- `hero_stats`（≤5）：决策级数据卡，如"推荐点位 SITE-X""综合得分 8.2/10""盈亏平衡客流 1,847 人/日""预测区间 ±12%"；
- `charts`（≤8，渲染引擎上限 6——**优先 ≤6**）：每图 id/title/option，附 `table`（列 ≥2，与图同源）；全部数字只取 20-analysis/30-model 已登记值，**禁止未入稿、不可比、编造数值进图**；
- option 中的颜色用商务蓝体系；数字格式与正文一致（千分位、单位、小数位）。

## 5. 一致性自核（成文后、渲染前，对照检查一次）

1. 正文每个数字都能在 20-analysis/30-model 中找到同值出处；
2. 每张图的数据与配套 table 同源；
3. 最高级断言与配方输出方向、并列情况一致；
4. 无内部编号/路径/字段名/recipe 名泄漏；
5. 模拟标识在标题区、图表、免责声明三处可见；
6. 排除维度、降级项、未计算项（如 NPV/IRR）都有显式声明。
